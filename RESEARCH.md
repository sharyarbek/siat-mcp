# SIAT → MCP: исследование (до реализации)

Дата: 2026-11-18. Всё, что ниже помечено «проверено», запрошено у живого API в этот день.

> Это документ разведки, написанный **до** реализации. Схема БД и названия инструментов в §3 и §5 — черновые;
> то, что получилось в итоге, описано в `ARCHITECTURE.md` и `README.md`. Итоговые решения — в §7.

---

## 0. TL;DR: главный вывод меняет исходный план

**siat.stat.uz — это не сайт со статьями, а SPA на Vue поверх открытого JSON API.**
Каждый график и таблица на сайте рисуется в браузере из чисел, которые отдаёт API. Картинок с данными там нет.

Что из этого следует:

| Пункт с доски | Что получается на самом деле |
|---|---|
| «Спарсить сайт» | HTML парсить не нужно. Нужен **ingest JSON API** (это проще, надёжнее, и значения приходят прямо из первоисточника) |
| «3000+ doc» | Проверено: **3261 листовой индикатор** в дереве глубиной 3 |
| «→ structured» | Данные **уже структурированы**: регион × период → значение, плюс метаданные на 4 языках |
| «img-to-text / tabular» | **Для SIAT не нужно.** Проверено: `/table/` и `/graphics/` отдают побайтово одинаковый JSON, а `cartogram`, `rating` и `compare-regions` отдают те же числа. «Новости» (`/all-news`) берутся из `/announcements/`: это только уведомления «индикатор обновлён». В 633 записях за 2023–2026 нет ни одного `<img>` или `<table>`. Это может пригодиться для lex.uz и PDF-методик, см. §6 |
| «Embed → VDB, RAG» | Векторный поиск нужен только для **поиска индикатора по смыслу**. Сами числа должны лежать в SQL |
| «MCP» | Да, MCP-сервер поверх локальной БД, см. §4–5 |

## 1. Что такое SIAT технически (проверено)

- Фронтенд: `https://siat.stat.uz` (Vue 2 + Vuetify), бандл `/js/app.*.js`.
- API: `https://siat.stat.uz/api` (то же самое на `https://api.siat.stat.uz`). Бэкенд похож на Django REST Framework: пагинация `count/next/previous/results`, `size=100`.
- Swagger, redoc и openapi не опубликованы (404). Эндпоинты я восстановил из JS-бандла.
- `robots.txt`: `Allow: /` для всех, ClaudeBot и GPTBot разрешены явно. Есть `sitemap.xml`.
- Заголовков rate-limit в ответах нет, Cloudflare на API нет. Но лимит запросов есть, он обнаружился позже (`429`, см. §8).
- Язык ответа: заголовок `Accept-Language` (`uz`, `uzc`, `ru`, `en`). Но почти все объекты и так содержат `name_uz`, `name_uzc`, `name_ru` и `name_en` одновременно.

### 1.1 Карта эндпоинтов

| Эндпоинт | Что отдаёт |
|---|---|
| `GET /sdmx/` | 5 корневых разделов (экономика, соцстат, экология, 30-летние макро ×2) |
| `GET /sdmx/json/` | **всё дерево целиком** одним запросом (~3 MB) |
| `GET /sdmx/last-layer/?page=N` | плоский список всех 3261 листьев (пагинированный) |
| `GET /sdmx/{id}/children/` | дочерние узлы |
| `GET /sdmx/{id}/` | карточка индикатора (code, имена, `updated_xlsx`, `view_options`…) |
| `GET /sdmx/{id}/metadata/` | 16 полей метаданных ×4 языка: единица измерения, периодичность, методика (ссылка на lib.stat.uz), источник, примечание, даты публикации и изменения |
| `GET /sdmx/{id}/table/` | **данные**: список регионов, у каждого `data: [{"2023-Q1": 40416.3}, …]` |
| `GET /sdmx/{id}/years/` | список периодов |
| `GET /sdmx/{id}/regions/` | список регионов |
| `/graphics/`, `/cartogram/`, `/rating/`, `/compare-regions/`, `/comparative-ratio/` | те же данные под разные виджеты (дубли `/table/`) |
| `/gistogram/`, `/gistogram/{region}/` | на проверенных индикаторах отдают `{}`, назначение не выяснено |
| `GET /sdmx/{id}/table/download/` | ссылки на файлы: `file` (SDMX-подобный XML) и `file_2` (v2 JSON: метаданные и значения в одном файле, **но имена только на узбекской кириллице**) |
| `GET /sdmx/search/?q=…&mode=name\|code` | Elasticsearch-поиск. Проверено два запроса: `q=aholi` (узб. латиница) дал 867 результатов, `q=Население` дал 0. Английский и кириллический узбекский не проверял. Для MCP надёжнее свой индекс |
| `GET /announcements/` | **54 533 уведомления** (с 2023-02 по сей день) вида «индикатор X обновлён, дата». `id` лежит внутри HTML-ссылки `reports-filed/{id}/` во всех 633 проверенных записях. Это пригодно как change-feed (id надо доставать regex-ом) |
| `/chat-api` | у сайта уже есть свой AI-чат (прецедент, не наша зависимость) |

### 1.2 Модель данных

```
Раздел (1.00.00) → Подраздел (1.03.00) → Группа (1.03.01) → Индикатор (1.03.01.0005, id=2943)
                                                                │
                                         table: Регион(15 шт., код СОАТО 1700, 1735, 1726…) × Период → число
```

- ⚠ **Уточнено пилотом 2026-11-19:** строки — это элементы классификатора индикатора («разрез»), а не обязательно регионы. Бывают Регионы (~85%), Вид деятельности, Страны, Продукты, Возрастные группы и др. См. ARCHITECTURE.md §4.
- Строк в таблице **1 или 15**: только Республика или Республика плюс 14 регионов (СОАТО-коды). В выборке из 20 индикаторов 15 строк было у 15, одна строка у 5.
- Районы: у 1 из 20 индикаторов (id=299) стоит `show_districts = true`, но `/table/` всё равно отдаёт 15 строк. Эндпоинт с данными по районам я не нашёл, это открытый вопрос.
- Периодичность: годовые 2355, квартальные 445, месячные 339, «не обновляемые» 122.
- Форматы периодов: `2025`, `2025-Q3`, `2025-M09`.

### 1.3 Подводные камни, которые влияют на схему (проверено)

1. **Разрезы зашиты в отдельные индикаторы**, а не в измерения. Например «Население по возрастным группам (18-19) (мужчины)» — это отдельный индикатор. Значит:
   - пол, возраст, продукт и т.п. приходится извлекать из названия (опциональный шаг обогащения);
   - либо принять как есть, и тогда поиск индикатора становится ключевой функцией.
2. **Смешанная гранулярность в одном ряду.** Например, у id=3664 периоды идут от `2018` до `2025-Q4`. В БД нужно хранить отдельно `period_type` (Y/Q/M) и `period_start`.
3. **Пустые таблицы бывают.** Например, у id=3892 0 строк.
4. **0 и «нет данных» неотличимы.** API отдаёт заголовок `x-siat-missing-values: zero`. У Ташкента по сельхоз-индикатору все нули, и формат не позволяет понять, это настоящий ноль или пропуск. v2 JSON тоже содержит `0.0`. Это нужно явно сообщать LLM в описании инструмента.
5. **Нарастающий итог.** Кумулятивность с начала года видна в данных:
   - у id=2943 (кварталы): Q1=40k, Q2=159k, Q3=300k, Q4=434k;
   - у id=2878 и id=1160 (месяцы) значения тоже монотонно растут внутри года.

   **Явного флага в метаданных нет** (у 2878 в примечании просто «By months»). Набор полей метаданных у разных индикаторов разный (12–16 полей), позиции не стабильны. Значит, кумулятивность надо определять эвристикой (рост внутри года со сбросом в январе или Q1) и честно помечать как «вероятно». Без этого модель будет складывать периоды и получать чушь.
6. **Единицы и цены** («в действующих ценах, млрд сум») есть только в метаданных. Поэтому их нужно отдавать вместе с каждым ответом с числами.
7. В метаданных есть ФИО, телефоны и email ответственных сотрудников. **В индекс и ответы их не тащим.**

## 2. Почему не «обычный RAG» (и где он всё-таки нужен)

Наивный RAG (страница → чанки → эмбеддинги → top-k → LLM) ломается на статистике:

- **Чанкинг рвёт таблицы:** шапка оказывается в одном чанке, а строки в другом, и значения теряют привязку к региону и году.
- **LLM не умеет агрегировать по чанкам.** Вопросы «топ-5 регионов по росту за 5 лет» или «доля Ташкента в республике» требуют вычислений по всей таблице, а не похожего текста.
- **Числа плохо эмбеддятся:** у «368923.0» и «368932.0» почти одинаковые векторы.
- **Точность:** статистике нужна воспроизводимость и ссылка на источник с кодом индикатора.

**Правильное разделение (как на доске, но с уточнением):**

| Что | Куда | Зачем |
|---|---|---|
| Названия индикаторов (4 языка), путь в дереве, методика, примечания, единицы | **FTS (BM25) + векторный индекс** | найти *какой* индикатор нужен по вопросу на любом языке |
| Значения | **SQL (SQLite или DuckDB), long-формат** | точная выборка, фильтры, агрегации |
| Связка | **MCP-инструменты** | LLM сама сначала ищет индикатор, потом берёт данные, потом считает |

То есть RAG остаётся, но только как **retrieval по каталогу из 3261 карточки**, а не по данным. Карточка индикатора (название, путь, единица, периодичность, методика) — это естественный «чанк», резать ничего не надо.

## 3. Предлагаемая архитектура

```
             ┌──────────── ingest (cron / по announcements) ───────────┐
siat API ──► │ crawler: /sdmx/json/ → для каждого листа: metadata+table  │
             │ (или download→v2 JSON: 1 запрос = метаданные+значения)    │
             └───────────────┬──────────────────────────────────────────┘
                             ▼
                 SQLite/DuckDB  ──►  FTS5 + эмбеддинги (каталог)
                             ▼
                      MCP server (stdio / Streamable HTTP)
                             ▼
              Claude Desktop / Claude Code / любой MCP-клиент
```

### 3.1 Схема БД (черновик)

```sql
node(id, parent_id, code, level, name_uz, name_uzc, name_ru, name_en, is_leaf)
indicator(id → node, code, periodicity, unit_*, methodology_url, note_*, source_*,
          first_published, last_modified, updated_xlsx, is_cumulative?, raw_meta JSON)
region(code PK /*СОАТО*/, name_uz, name_uzc, name_ru, name_en, parent_code)
observation(indicator_id, region_code, period TEXT, period_type CHAR(1) /*Y|Q|M*/,
            period_start DATE, value REAL, PRIMARY KEY(indicator_id, region_code, period))
sync_state(indicator_id, fetched_at, source_change_date, etag/hash)
```

Объём: 3261 индикатор × до 15 регионов × ~16–200 периодов, это порядка 1–3 млн строк. Помещается в один файл SQLite на десятки МБ.

### 3.2 Ingest

- **Полная загрузка:** 1 запрос за деревом плюс 3261 × (`/metadata/` + `/table/`), то есть ~6.5k запросов. При 3 параллельных запросах это ~10–20 минут. Это основной путь, потому что здесь все 4 языка. v2 JSON содержит только узбекскую кириллицу, его можно брать как запасной вариант.
- Даты в источниках расходятся: у 2943 «последнее изменение» в XML 2026-11-09, а в `/metadata/` 2026-04-28. Поэтому ключ для sync — `updated_xlsx` из карточки и дерева.
- **Инкрементальное обновление:** читаем `/announcements/` до последней виденной даты и перекачиваем только упомянутые `id`. Страховка: раз в неделю сверять `updated_xlsx` из дерева.
- Хранить сырой JSON (`raw/`) рядом с БД, чтобы можно было пересобрать её без повторного обхода.

### 3.3 Live-прокси против ingest

| | Live-прокси (MCP сразу ходит в API) | Ingest + локальная БД |
|---|---|---|
| Свежесть | всегда актуально | задержка до следующего sync |
| Поиск | только ES-поиск сайта (только латиница) | свой поиск на 4 языках + семантика |
| Аналитика по многим индикаторам | N запросов в чужой API | один SQL-запрос |
| Устойчивость | зависит от их аптайма | работает офлайн |

**Рекомендация:** ingest плюс инкрементальный sync. Опционально инструмент `refresh_indicator(id)`, который подтягивает свежие данные live.

## 4. MCP: что это и как устроено

**Model Context Protocol** — открытый протокол (JSON-RPC 2.0), через который LLM-приложение (*host/client*: Claude Desktop, Claude Code, IDE) подключается к внешнему *server*, который даёт доступ к данным и действиям. Примерно как «USB-C для LLM»: один раз пишешь сервер, и он работает в любом совместимом клиенте.

### 4.1 Три примитива сервера

| Примитив | Кто инициирует | Для SIAT |
|---|---|---|
| **Tools** — функции с JSON-Schema входа (и, опционально, выхода `outputSchema` → `structuredContent`) | модель решает вызвать | `search_indicators`, `get_series`, `compare_regions`… |
| **Resources** — адресуемые данные по URI | приложение или пользователь подключает в контекст | `siat://indicator/2943`, `siat://catalog/1.03.00` |
| **Prompts** — шаблоны сценариев | пользователь выбирает | «Сравни регионы по индикатору», «Динамика за N лет» |

### 4.2 Транспорты

- **stdio:** клиент запускает сервер как подпроцесс. Подходит для локального режима (Claude Desktop / Claude Code). Начинать стоит с него.
- **Streamable HTTP:** сервер по сети, подходит для общего доступа команде. Старый HTTP+SSE deprecated.

### 4.3 Актуальная версия спецификации

Текущая ревизия — **2026-07-28** (предыдущая 2025-11-25). Ключевые изменения, которые нас касаются:

- Протокол стал **stateless**: убрали handshake `initialize` и `Mcp-Session-Id`, добавили обязательный `server/discover`, а версия и capabilities передаются в `_meta` каждого запроса.
- `inputSchema`/`outputSchema` теперь допускают любой JSON Schema 2020-12, а `structuredContent` — любое JSON-значение. Это удобно для отдачи таблиц.
- Результаты `tools/list` и `resources/read` несут `ttlMs`/`cacheScope`, а `tools/list` рекомендуется отдавать в детерминированном порядке.
- **Sampling, Roots и Logging deprecated.** Логи пишем в stderr или OpenTelemetry.
- `tasks` вынесены в расширение. Пригодится, если запускать длинный sync как задачу.

Практически: берём официальный SDK последней версии, и он сам закрывает протокольные детали. В проекте используется Python-пакет `mcp` 2.3 (класс `MCPServer`).

### 4.4 Почему MCP здесь лучше «RAG в промпт»

Модель сама планирует цепочку: «найти индикатор → посмотреть метаданные (единицы, кумулятивность) → взять ряд → посчитать». Каждый шаг даёт точные структурированные данные, а не текстовые обрывки. Плюс один сервер работает во всех клиентах.

## 5. Черновик набора инструментов MCP

Принцип: **мало инструментов, но мощных**; каждый ответ компактный, с единицами и источником.

| Tool | Вход | Выход |
|---|---|---|
| `search_indicators` | `query` (любой язык), `section_code?`, `periodicity?`, `limit` | список `{id, code, name, path, unit, periodicity, years_range}`. Гибрид BM25 + вектор |
| `browse_catalog` | `code?` (узел дерева) | дочерние узлы, для навигации |
| `get_indicator` | `id` или `code`, `lang` | полные метаданные: единица, методика, примечание, периоды, регионы, флаг кумулятивности |
| `get_data` | `id`, `regions?`, `period_from?`, `period_to?`, `period_type?`, `format: long\|wide` | таблица плюс `unit`, `source_url`, `last_modified`, предупреждение «0 может означать нет данных» |
| `compare_regions` | `id`, `period`, `sort`, `top?` | рейтинг регионов, доли от республики |
| `query_sql` *(опционально, read-only)* | `sql` | для сложной аналитики по нескольким индикаторам. Только SELECT, с лимитом строк |
| `refresh_indicator` *(опц.)* | `id` | перекачать из live API |

Resources: `siat://indicator/{id}` (карточка и данные в Markdown/CSV), `siat://catalog`.
Prompts: `regional_comparison`, `trend_analysis`.

В каждом ответе с числами указывать: **единицу, периодичность, кумулятивность, дату обновления, ссылку** `https://siat.stat.uz/reports-filed/{id}/...`.

## 6. Image-to-text / image-to-table: где это реально нужно

**Для SIAT не нужно.** Графики рисуются из того же JSON, что и таблица. Распознавать картинку графика значит получить *хуже* те же числа, которые API отдаёт точно.

Где это может понадобиться (если расширяем scope):

- **lex.uz** (вторая звёздочка на доске): нормативные акты, там таблицы бывают HTML-ными, бывают сканами и картинками. Я его ещё **не исследовал**.
- **lib.stat.uz**: методики, на которые ссылаются метаданные. Скорее всего PDF/HTML.
- PDF-бюллетени и пресс-релизы stat.uz (stat.uz отдал 403 на curl, его тоже надо смотреть отдельно).

Классы инструментов, если понадобится:

- **Пайплайны разбора документов** (PDF и сканы → Markdown/HTML-таблицы): Docling (TableFormer), MinerU, PaddleOCR / PaddleOCR-VL, Marker, olmOCR. Сравнения в сети в основном от вендоров и агрегаторов, поэтому выбирать надо **на своих 20–30 образцах**, а не по чужим рейтингам.
- **VLM** (Claude, Qwen-VL и т.п.) для таблиц-картинок и **графиков → данные**. Chart-to-table остаётся самой слабой областью у всех инструментов, поэтому результат надо помечать как «оцифровано с изображения, приблизительно».

Предложение: сделать это **отдельным опциональным модулем** с тем же контрактом (документ → структурированные таблицы и текст с указанием источника и confidence) и подключать его только для источников, где данных в машинном виде нет.

## 7. Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Охват | только SIAT, все 3261 индикатор | «3000+» из задания — это и есть SIAT; lex.uz и PDF-методики — отдельная задача |
| Image-to-table | для SIAT не используется | графики рисуются из того же JSON, что и таблица (проверено, §0 и §6); модуль распознавания — на случай PDF-источников |
| Архитектура | скачивание в локальную БД, а не live-запросы к API | у API есть лимит запросов (§8), а аналитика по многим индикаторам — это один SQL-запрос вместо сотен HTTP |
| Стек | Python 3.12, uv, официальный SDK `mcp` 2.x, SQLite + FTS5 | минимум зависимостей; всё ставится в локальный `.venv` |
| Поиск | полнотекстовый (FTS5, триграммы, BM25) по 4 языкам, без векторов | замер: нужный индикатор в top-5 на 21 из 21 тестового запроса; векторы добавим, если появятся промахи |
| Интерфейс | только MCP, локально через stdio | работает в Claude Code / Claude Desktop / любом MCP-клиенте; отдельный REST API не нужен |
| Разрезы из названий (пол, возраст…) | не разбираются, оставлено на будущее | поиск по названию уже находит нужный вариант индикатора |

## 8. Дополнение (2026-11-19)

**Охват.** «3000+» из задания — это ровно 3261 индикатор SIAT, поэтому scope v1 = SIAT. Внешние ссылки внутри метаданных: в выборке из 80 индикаторов 335 ссылок ведут на lib.stat.uz (методики, часть из них PDF-приказы вида `84-buyruq_compressed.pdf`), 6 на lex.uz и 5 на imv.uz.

**Картинки внутри 3261 индикатора.** В 80 случайных карточках и метаданных нет ни `<img>`, ни `<table>`, ни base64. Все визуализации сайта рисуются из JSON. Картинки или сканы возможны только в PDF-методиках на lib.stat.uz. Они не проверялись: lib.stat.uz отвечает 403 на не-браузерные запросы, а обходить эту защиту без согласования не стали.

**Rate limit (новое, важно для crawler).** После ~150 быстрых запросов API начал отвечать `429 Too Many Requests` с заголовком `Retry-After: 6`. Значит:
- crawler должен уважать `Retry-After` и держать паузу между запросами;
- по факту полная загрузка (~9.5k запросов: карточка, метаданные и таблица на индикатор) шла ~2.7 запроса в секунду, ни одного `429`, около часа; это разовая операция;
- live-режим, где модель на каждый вопрос делает много запросов, будет упираться в лимит. Это ещё один аргумент за локальную БД.

**Provenance / ссылки на источник (требование преподавателя).** Каждый ответ с числами и каждая визуализация несут блок `source`:
- организация (из поля «Official statistics preparer»), название и код индикатора;
- URL на siat (`https://siat.stat.uz/reports-filed/{id}/...`);
- единица измерения и периодичность;
- дата последнего обновления у источника и дата нашей загрузки;
- если значение получено с изображения или PDF, то документ, страница и пометка «оцифровано».

**Разрезы в названиях (пример).** В узле «Демография > Демографические показатели» 163 индикатора-соседа: «население (всего)», «(мужчины)», «(женщины)», «(город)», «(село)», «(мужчины, в городской местности)» и т.д. Пол, тип местности и возраст закодированы в названии.

## 9. Общие принципы, которые легли в проект

1. **Ссылку на источник формирует код, а не модель.** Инструмент сам кладёт в ответ блок `source` (код индикатора, URL, дата обновления, готовая цитата). Модели остаётся только его привести.
2. **Считает код.** Рейтинги, доли, проценты и среднегодовой темп возвращают инструменты. Модель не складывает числа сама.
3. **Честный отказ вместо догадки.** Если данных за период нет, инструмент так и говорит, и модель должна передать это пользователю.
4. **Сырые ответы хранятся рядом с базой.** Базу можно пересобрать без повторного обхода сайта, а скачивание докачивается с места остановки.
5. **Качество измеряется, а не предполагается.** Эталонные ответы генерируются из самой базы (значение, лидер, изменение, «нет данных»), а ответы модели сверяются с ними точным сравнением чисел.
6. **Векторный поиск — только если он нужен по замерам.** Сначала полнотекстовый поиск по 4 языкам; векторы добавляются, если проверка поиска покажет промахи.
