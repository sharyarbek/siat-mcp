## 1. Откуда требования: доска → компоненты

Единственный источник требований — фото доски. Каждая пометка на ней ложится на конкретный компонент:

| На доске | Что это значит у нас | Компонент |
|---|---|---|
| `siat.stat.uz`, `3000+`, `doc` | 3261 индикатор SIAT | Collector |
| `→ structured` | индикатор × регион × период → значение, плюс метаданные | Loader → SQLite |
| `txt` → поиск | названия и методики на 4 языках — это то, *по чему ищем* | FTS5-индекс каталога |
| таблица → `db` | числа хранятся в SQL, их не режем на чанки | таблица `observation` |
| графики и карты (`img-to-text / tabular`) | на SIAT они рисуются из того же JSON, поэтому OCR не нужен. Храним данные плюс **ссылку на каждый вид визуализации** | provenance |
| `Embed → VDB, RAG` | семантический поиск — опция v2, если FTS не хватит | (later) |
| `+ MCP` | интерфейс, через который LLM работает с данными | MCP-сервер |
| `loop` | агентный цикл: модель вызывает инструменты, пока не соберёт ответ | MCP-клиент (Claude) |

## 2. Общая схема

```
                        ┌──────────────────── ОФЛАЙН (по расписанию) ────────────────────┐
                        │                                                                 │
 siat.stat.uz/api ──►  [1] Collector ──► [2] Raw store ──► [3] Loader ──► [4] SQLite      │
   (лимит 429)          (вежливый,        data/raw/*.json    (нормализация,   siat.db      │
                         докачка)         + crawl state       без ПДн)        + FTS5       │
        ▲                                                                       │         │
        └──── [7] Sync: /announcements/ → какие id обновились → снова [1]→[3]   │         │
                        └───────────────────────────────────────────────────────┼─────────┘
                                                                                ▼
                                                              [5] Core (Python-функции)
                                                         поиск · выборка · вычисления · source
                                                                                │
                                                              [6] MCP-сервер (stdio)
                                                                                │
                                                         Claude Desktop / Claude Code (агент)
                                                                                │
                                                              [8] Eval: вопросы с эталоном
```

Главный принцип: **числа считает код, а модель только выбирает инструменты и формулирует ответ.**

Каждое число, которое возвращает инструмент:
- взято из БД или посчитано кодом;
- снабжено блоком `source` со ссылкой.

> Важная оговорка, которую нужно знать честно: в режиме MCP финальный текст пишет модель-клиент, и наш сервер этот текст **не видит**. Поэтому проверить, что модель не исказила число в своём ответе, сервер не может. Гарантия сервера звучит так: «всё, что вернули инструменты, точно и со ссылкой». Проверку итоговых ответов делает отдельный eval-прогон (§8).

## 3. Компоненты по слоям

### [1] Collector: скачивание

- **Что качаем:**
  - `GET /sdmx/json/` — дерево, 1 запрос;
  - на каждый из 3261 листьев три запроса: `/sdmx/{id}/` (карточка: `view_options`, `classifier`, `updated_xlsx`), `/sdmx/{id}/metadata/` и `/sdmx/{id}/table/`.
- **Объём:** ~9.8k запросов.
- **Вежливость:**
  - адаптивная скорость: стартуем примерно с 1 запроса в секунду;
  - на `429` ждём `Retry-After` (сервер просит ~6 с) и замедляемся;
  - 5xx и сетевые ошибки повторяем с экспоненциальной паузой;
  - честный `User-Agent`.

  Оценка времени первого прогона — **2–3 часа, один раз**.
- **Докачка (resumable):** состояние каждого `(id, endpoint)` хранится в `data/crawl.sqlite`: статус, время, sha256 ответа. Если процесс упал, после перезапуска он продолжает с того же места.
- Collector **ничего не знает о схеме БД**, он только сохраняет ответы как есть. Поэтому его можно запустить уже сегодня.

### [2] Raw store

- `data/raw/tree.json`, `data/raw/{id}/card.json`, `metadata.json`, `table.json`. Это неизменённые ответы API.
- Зачем: БД можно пересобрать без повторного скачивания, всё воспроизводимо, есть что отлаживать.
- Объём: десятки МБ (замерим).
- ⚠ В сырых файлах есть ФИО, телефоны и e-mail сотрудников. Поэтому `data/` исключаем из git (`.gitignore`), а в БД, индекс и ответы эти поля не попадают.

### [3] Loader: raw → SQLite

- Парсит raw-файлы, нормализует и пишет в БД. Операция идемпотентна: перезапуск даёт тот же результат.
- **Периоды:**
  - `2025` → `Y`;
  - `2025-Q3` → `Q`;
  - `2025-M09` → `M`.

  Для каждого вычисляются `period_start` и `period_end`. Внутри одного ряда типы периодов бывают смешаны (пример: id=3664), поэтому тип храним в каждой строке.
- **Метаданные** храним строками «ключ → значение», а не фиксированными колонками. У разных индикаторов от 12 до 16 полей, порядок плавает, подписи различаются. Ключ нормализуем по словарю синонимов: «Unit of measurement» → `unit`, «Periodicity» → `periodicity` и т.д. Поля с ПДн отбрасываем.
- **Флаги качества:**
  - `table_empty`;
  - `zero_may_mean_missing` — API прямо пишет в заголовке, что пропуски заменены нулями;
  - `cumulative_likely` — эвристика: значения монотонно растут внутри года и сбрасываются в Q1 или январе.

  Флаги — это **подсказки, а не факты**, так их и отдаём.
- Строит **FTS5-индекс** каталога: названия на uz, uzc, ru и en, путь в дереве, единица измерения, примечание.
  - **Морфология.** У стандартного токенизатора FTS5 нет стемминга для русского и узбекского: «безработица» не найдёт «безработицы», `aholi` не найдёт `aholining`. Поэтому используем токенизатор **`trigram`** (поиск по кусочкам из 3 символов, устойчив к окончаниям; проверено: SQLite 3.49.1 его поддерживает) плюс ранжирование BM25.
  - **Нормализация текста** одинаково для индекса и запроса: нижний регистр, все виды апострофов (`‘ ’ ʼ ' ʻ`) приводим к одному символу, ё → е.

### [4] SQLite: схема (черновик)

Один файл `data/siat.db`, без сервера.

> Схема **предварительная**: она построена по ~30 просмотренным индикаторам. Финальную версию фиксируем после пилотного скачивания (веха 1a). Защита от сюрпризов: исходную строку периода храним всегда, а для неизвестных форматов есть тип `X`.

```sql
node(id PK, parent_id, code, level, is_leaf, position,
     name_uz, name_uzc, name_ru, name_en)                 -- дерево (разделы + индикаторы)

classifier(id PK, name_uz, name_uzc, name_ru, name_en)    -- вид разреза: Регионы, Вид деятельности,
                                                          -- Страны, Продукты, Возрастная группа…
indicator(id PK → node, code, classifier_id, periodicity_raw, view_options JSON, updated_xlsx,
          n_items, n_obs, period_types, first_period, last_period,
          table_empty, has_zeros, cumulative_likely, fetched_at)

indicator_meta(indicator_id, key, lang, value,            -- только белый список ключей:
               PRIMARY KEY(indicator_id, key, lang))      -- unit, periodicity, methodology, method_short,
                                                          -- methodology_url, note, info_source, org_name,
                                                          -- classifiers, department (без ПДн)
item(indicator_id, code, position, is_root,               -- строки таблицы = элементы разреза
     name_uz, name_uzc, name_ru, name_en,                 -- (для Регионов code = СОАТО: 1700, 1735…)
     PRIMARY KEY(indicator_id, code))

observation(indicator_id, item_code, period /*исходная строка*/, period_type /*Y|Q|M|X*/,
            period_start, period_end, value REAL,
            PRIMARY KEY(indicator_id, item_code, period))

catalog_fts  -- FTS5(tokenize='trigram'): названия ×4 языка, путь, единица, разрез (нормализованные)
load_info(key, value)                                     -- дата снимка, счётчики, отчёт загрузки
```

> **Находка пилота (2026-11-19):** строки таблицы — это не всегда регионы, а элементы **классификатора** индикатора (на сайте колонка называется «Разрез»). В пилоте из 118 индикаторов: Регионы — 101, Вид деятельности (ОКЭД A, B, C…) — 10, по одному — Страны, Продукты (цены), Возрастная группа, Потребительские товары, ВСТ туризма, РСМТУ, СКП. Поэтому схема хранит общий «разрез» (`item`), а регион — его частный случай.
>
> Метаданные на сайте грязные: один и тот же ключ называется по-разному (`Номер телефона :` / `Номер телефона:`), ключи бывают на узбекском, ФИО встречается даже в имени ключа, у одного индикатора поля сдвинуты. Поэтому ключ определяем по русской подписи и сохраняем **только белый список**, остальное отбрасываем и считаем в отчёте загрузки.

Порядок объёма: 3261 индикатор × 1–15 регионов × 10–200 периодов, то есть ≲ 3 млн строк и десятки МБ.

### [5] Core: общие функции

Это обычные Python-функции, которые ничего не знают про MCP. Их можно тестировать без LLM.

- `search(query, filters)` → карточки индикаторов: FTS5 с ранжированием BM25 по всем 4 языкам.
- `get_indicator(id|code)` → метаданные, периоды, регионы, флаги.
- `get_series(id, regions, period_from, period_to, period_type)` → строки.
- `rank_regions(id, period)`, `change(id, region, from, to)` → вычисления: доля от республики, абсолютный и процентный рост.
- `build_source(id, view)` → блок источника (§5).

### [6] MCP-сервер

- Официальный Python SDK **`mcp` 2.x** (на 2026-11-19 актуальна 2.3.0). В версии 2.x сервер создаётся через `from mcp.server import MCPServer`.
  > В моих прошлых сообщениях был пример с `FastMCP` — это API версии 1.x, он устарел.
- Транспорт v1: **stdio** (локально). Streamable HTTP подключается одной опцией, если понадобится.
- Инструменты описаны в §4. Вывод двойной:
  - `structuredContent` — JSON для программ;
  - короткий текст или Markdown-таблица — для модели.

### [6b] Инструменты разработчика

- **MCP Inspector** (`mcp dev src/siat/server.py`) — «Swagger для MCP». Показывает в браузере список инструментов и их схемы и позволяет вызвать любой вручную.
- REST API + Swagger решили **не делать в v1**: работаем только через MCP. Если понадобится, это тонкий слой поверх Core, см. «later».

### [7] Sync: обновление данных

- Читаем `/announcements/` до последней обработанной даты, достаём из HTML-ссылок `reports-filed/{id}/` id индикаторов и перекачиваем их через [1]→[3].
- Раз в неделю делаем сверку: сравниваем `updated_xlsx` из дерева `/sdmx/json/` (поле есть у каждого листа — проверено) с БД, чтобы поймать то, что лента пропустила. Запасной сигнал — `lastmod` в `sitemap.xml`.
- Запуск командой `siat sync` вручную или по расписанию (Планировщик задач Windows / cron).

### [8] Eval: проверка качества

- **Уровень 1, без LLM (pytest):** функции Core сверяются с raw-данными. Ключ API не нужен.
- **Уровень 2, с LLM:** 30–50 вопросов. Эталонные ответы **генерируются из БД по шаблонам** («значение X в регионе R за год Y», «топ-3 региона», «рост за N лет»). Плюс вопросы-ловушки, на которые ответа в данных нет. Сравниваем числа точно и проверяем ссылку на источник.
  - **Вариант А:** гоняем вручную в Claude Desktop.
  - **Вариант Б:** скрипт на Anthropic Python SDK подключает наш MCP-сервер и прогоняет вопросы автоматически. Для этого нужен API-ключ.

## 4. Инструменты MCP (контракты v1)

| Tool | Вход | Выход | Ограничения |
|---|---|---|---|
| `search_indicators` | `query` (любой из 4 языков), `section_code?`, `periodicity?`, `breakdown?` (вид разреза), `limit≤20` | `[{id, code, name, path, unit, periodicity, breakdown, n_items, periods:[from,to]}]` | только каталог, без чисел |
| `browse_catalog` | `code?` (пусто — корень) | дочерние узлы | для навигации по дереву |
| `get_indicator` | `indicator` (id или код), `lang` | метаданные, список периодов и регионов, флаги, ссылки на все виды визуализаций | без ПДн |
| `get_data` | `indicator`, `items?` (коды или названия элементов разреза, например регионов), `period_from?`, `period_to?`, `period_type?`, `format: long\|wide` | строки + `unit`, `flags`, `source`, **`truncated: true/false`** | ≤ 500 строк; если строк больше, ответ помечается `truncated` и подсказывает сузить запрос (молча обрезать нельзя: суммы получатся неверные); **один `period_type` на ответ** |
| `rank_items` | `indicator`, `period`, `order`, `top?` | рейтинг элементов разреза (регионов, отраслей, стран…), доля каждого от итоговой строки (`is_root`), если она есть + `source` | для любого разреза с ≥2 элементами |
| `compute_change` | `indicator`, `item`, `from`, `to` | абсолютное изменение, % и среднегодовой темп + `source` | если `cumulative_likely`, выводим предупреждение |

Правила для всех инструментов:
- у каждого есть параметр `lang` (`uz` | `uzc` | `ru` | `en`, по умолчанию `ru`): на этом языке возвращаются названия и ссылки;
- в каждом числовом ответе есть `unit`, `snapshot_date` (когда мы скачали) и предупреждения (`zero_may_mean_missing`, `cumulative_likely`);
- в каждом ответе есть `source` (§5);
- ошибки возвращаются понятным текстом с подсказкой, что делать, например: «индикатор не найден — попробуй search_indicators».

**Resources (v1):** `siat://indicator/{id}` — карточка индикатора в Markdown.
**Prompts (v1):** `regional_comparison`, `trend_analysis` — готовые сценарии для пользователя.

## 5. Provenance: ссылка на источник у каждого числа и визуализации

Ссылок два вида, оба проверены:

**1. Основная ссылка-цитата:** `https://siat.stat.uz/data/{id}/?lang=ru|uz|uzc|en`.
- Это статическая страница, которую сервер отдаёт сразу готовой, без JavaScript.
- На ней на нужном языке есть название, код, дата «Обновлено» и **полная таблица** значений.
- Она подходит для цитаты лучше всего: открывается у любого и показывает ровно те числа, что у нас.

**2. Ссылки на конкретные визуализации** в интерактивном интерфейсе. Шаблон URL взят из JS-кода сайта. Язык эти страницы берут из настроек браузера, по умолчанию узбекская кириллица.

```
https://siat.stat.uz/reports-filed/{id}/{view}
```

`view` берётся из `view_options` конкретного индикатора:

| view_options | slug в URL | что это |
|---|---|---|
| metadata | `meta-data` | метаданные |
| table | `table-data` | таблица |
| graphics | `line-data` | линейный график |
| gistogram | `bar-data` | гистограмма |
| cartogram | `map-data` | карта |
| rating | `rate-data` | рейтинг регионов |
| compare_regions | `compare-data` | сравнение регионов |
| comparative_ratio | `relationship-data` | соотношение |
| customization | `custom-data` | конструктор |

Блок, который возвращается вместе с данными:

```json
"source": {
  "publisher": "<из метаданных индикатора: поле «подготовитель официальной статистики»>",
  "primary_source": "<из метаданных: «первичный источник информации»>",
  "indicator_code": "1.03.01.0005",
  "indicator_name": "Общий объем продукции сельского, лесного и рыбного хозяйства (квартальная)",
  "unit": "млрд сум, в действующих ценах",
  "url": "https://siat.stat.uz/data/2943/?lang=ru",
  "views": {
    "table":  "https://siat.stat.uz/reports-filed/2943/table-data",
    "chart":  "https://siat.stat.uz/reports-filed/2943/line-data",
    "map":    "https://siat.stat.uz/reports-filed/2943/map-data",
    "meta":   "https://siat.stat.uz/reports-filed/2943/meta-data"
  },
  "api": "https://siat.stat.uz/api/sdmx/2943/table/",
  "source_updated": "2026-11-09",      // = updated_xlsx; ровно эту дату сайт показывает как «Обновлено»
  "snapshot_date": "2026-11-19",
  "citation": "Источник: SIAT (siat.stat.uz), индикатор 1.03.01.0005, данные на 09.11.2026"
}
```

Строку `citation` модель вставляет под ответом или графиком как есть, без пересказа. Блок собирает код, поэтому модель не может «придумать» ссылку.

Правила заполнения:
- `publisher` и `primary_source` берём **из метаданных каждого индикатора**, а не из константы: источники бывают разные, встречались ссылки на Минфин (imv.uz);
- дата в цитате — всегда `updated_xlsx`. Дата «последнего изменения» в метаданных бывает другой, у 2943 расхождение было в полгода.

## 6. Стек

| Что | Выбор | Почему |
|---|---|---|
| Язык | Python 3.12 (уже установлен) | библиотеки для данных и официальный MCP SDK |
| Окружение | `uv` (установлен, 0.12) | одна команда ставит зависимости, есть lock-файл |
| HTTP | `httpx` | таймауты, повторы, простой код |
| БД | SQLite + FTS5 (встроены в Python) | один файл, без сервера, полнотекстовый поиск из коробки |
| MCP | `mcp[cli]` 2.x (`MCPServer`) + MCP Inspector | официальный SDK; Inspector — «Swagger для MCP» |
| Модели данных | `pydantic` | схемы входа и выхода инструментов |
| Экспорт | `pyarrow` → Parquet + CSV | «structured» датасет как отдельный результат |
| Тесты | `pytest` | уровень 1 eval |
| Eval уровня 2 (опц.) | `anthropic` SDK | автопрогон вопросов через Claude |

## 8. Порядок работ (вехи)

| # | Что | Результат |
|---|---|---|
| **0** | Hello-world MCP: сервер с одним инструментом `ping`/`add`, подключённый к твоему клиенту | убедились, что SDK, конфиг и клиент работают; первая работающая штука в первый же день |
| 1a | Collector + **пилот на ~100 индикаторах** | меряем реальный лимит, видим реальные данные |
| 1b | Loader + схема + **один инструмент** на пилотных данных | сквозной результат на маленьком срезе: скачали → БД → Claude ответил со ссылкой |
| 1c | Полное скачивание 3261 индикатора | полный raw-снимок (оценка 2–3 часа, уточним по пилоту) |
| 2 | Схема финал + FTS + экспорт Parquet/CSV + **проверка поиска на ~20 запросах** | `siat.db` + structured-датасет + цифра качества поиска |
| 3 | Core + MCP-инструменты + provenance | Claude отвечает на вопросы по SIAT со ссылками |
| 4 | Eval: pytest + 30–50 вопросов | цифра точности |
| 5 | Sync | данные обновляются сами |

Шаги 0 и 1a независимы, их можно делать параллельно.

Детали вехи 0:
- клиент — **Claude Code**, ты уже в нём работаешь;
- регистрация: `claude mcp add <name> -- <команда запуска>` (синтаксис сверен с `claude mcp --help`);
- правило stdio-сервера: **никогда не печатать в stdout**, потому что это канал протокола. Логи пишем в stderr.

## 9. Что НЕ входит в v1 (later)

- Векторный или гибридный поиск (e5-small + RRF). Добавим, если проверка поиска в вехе 2 покажет промахи trigram-FTS.
- Разбор разрезов из названий (пол, возраст, город/село) в отдельные поля.
- Разбор PDF-методик с lib.stat.uz (здесь мог бы пригодиться img-to-table). Сайт блокирует не-браузерные запросы, это нужно согласовывать отдельно.
- Районы: у части индикаторов есть флаг `show_districts`, но фронтенд его не использует, а эндпоинт с районными данными не найден.
- HTTP-транспорт MCP и деплой на сервер. REST API в v1 запускается локально.
- REST API + Swagger (FastAPI) поверх Core и `POST /v1/ask` — если понадобится проверка по HTTP.
- Рендер картинок-графиков внутри MCP. Пока отдаём данные и ссылку на график сайта, а нарисовать по данным может сам клиент.

## 10. Риски

| Риск | Что делаем |
|---|---|
| Лимит 429 / блокировка | адаптивная скорость, `Retry-After`, ночной прогон, кэш raw |
| API без документации может поменяться | raw store + тесты Loader; при поломке видно, где именно |
| Ноль вместо пропуска | флаг + текст предупреждения в каждом ответе |
| Кумулятивные ряды | эвристика + предупреждение; `compute_change` не суммирует периоды |
| Модель исказит число в финальном тексте | готовая строка `citation`, компактные ответы, eval уровня 2 |
| ПДн в метаданных | фильтр в Loader, `data/` не в git |
